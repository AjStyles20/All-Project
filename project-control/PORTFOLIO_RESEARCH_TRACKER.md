# AJ Project Portfolio — Research Tracker

## Purpose
This tracker prevents implementation enthusiasm from outrunning evidence. A project is not cleared for substantial implementation merely because it sounds promising. Research depth, prior art, feasibility, risks, and novelty threats must be recorded first.

## Status vocabulary
- NOT STARTED — no structured review yet.
- DISCOVERY — source discovery underway.
- SCREENING — candidate evidence being checked for relevance/quality.
- EVIDENCE BUILD — evidence matrix and lineage being populated.
- GAP REVIEW — prior art and novelty threats being compared.
- FEASIBILITY REVIEW — technical/cost/platform/security constraints being tested.
- DECISION READY — sufficient evidence exists for a bounded go/park/kill decision.
- PAUSED IMPLEMENTATION — implementation exists but is intentionally frozen pending portfolio review.
- CONDITIONAL GO — bounded theory/specification survives current review, but implementation/evaluation has not yet verified it.
- GO / PARK / KILL — AJ-approved portfolio decision.

## Evidence discipline
For every material claim, distinguish VERIFIED FACT, REASONED INFERENCE, UNVERIFIED HYPOTHESIS, and UNKNOWN. Do not convert “not found” into “does not exist.” Novelty claims must be bounded by the searches and evidence actually reviewed.

## Priority policy
Numeric project IDs are identifiers, not execution order. Opportunity and feasibility are scored separately because an attractive project may still be infeasible, while a feasible project may offer weak differentiation. Uncertainty should remain visible rather than be hidden by a single score.

## Required dossier for a decision-ready project
1. Project identity and bounded problem statement.
2. Historical/intellectual/technical lineage appropriate to the domain.
3. Evidence matrix with source provenance and claim strength.
4. Academic/research state of knowledge where applicable.
5. Commercial and product prior art.
6. Open-source/project prior art.
7. Relevant patents, standards, protocols, regulation, or platform policies where applicable.
8. Counterexamples and novelty threats.
9. Gap analysis that states what prior work does and does not establish.
10. Narrow, falsifiable novelty/differentiation statement.
11. User/problem evidence rather than feature-first reasoning.
12. Technical feasibility and architecture candidates.
13. Hardware/OS/API/provider constraints where applicable.
14. Security, privacy, safety, accessibility, and ethics review appropriate to the domain.
15. Cost, licensing, infrastructure, and third-party dependency review.
16. Rejected alternatives and reasons.
17. Known limitations and unresolved questions.
18. Go / Park / Kill recommendation with confidence and evidence boundaries.

## Cross-check policy
Important conclusions should not depend on a single discovery mechanism when independent corroboration is reasonably available. Use different source classes and research tools for different purposes. If credible sources conflict, preserve the conflict and resolve it explicitly where possible rather than silently choosing one.
